# NOOPI (누피) Blind Game Specification

## 1. 게임 개요

블라인드 게임은 정확히 두 명이 플레이하는 실시간 추리 게임이다.

서버는 두 Player에게 서로 다른 제시어를 하나씩 배정한다. 각 Player는
자신에게 배정된 제시어를 볼 수 없고 상대방에게 배정된 제시어만 볼 수
있다.

두 Player는 실제 현장에서 질문과 답변을 주고받으며 자신의 제시어를
추리한다.

서비스는 제시어 선정과 배정, 상대방 제시어 전달, 정답 제출과 판정, 승자
결정, 최종 결과 전달만 담당한다.

## 2. 참가 인원

-   최소: **2명**
-   권장: **2명**
-   최대: **2명**

게임 시작 시 정상적으로 참가 중인 GameSession 참가자가 정확히 두 명인지
서버가 검증한다.

Frontend는 선택 가능 여부를 안내할 수 있지만 최종 검증 책임은 서버에
있다.

## 3. 제시어 선정

게임 시작 시 서버는 전체 활성 제시어 풀에서 서로 다른 제시어 두 개를
선정한다.

제시어에 내부 카테고리 정보가 존재할 수 있으나 블라인드 게임에서는
카테고리를 선택하거나 공개하지 않는다.

따라서 다음 UI와 API는 블라인드 게임에 제공하지 않는다.

``` text
카테고리 선택
카테고리 공개
전체 제시어 목록 조회
```

선택 가능한 서로 다른 활성 제시어가 두 개 미만이면 게임을 시작할 수
없다.

## 4. 제시어 배정

두 Player를 A와 B라고 할 때 서버는 서로 다른 제시어를 하나씩 배정한다.

예:

``` text
A의 실제 제시어: 피자
B의 실제 제시어: 기린
```

배정은 GameSession마다 새롭게 수행하며 이전 게임의 배정 결과는 다음
게임에 영향을 주지 않는다.

## 5. 제시어 공개 원칙

각 Player에게는 상대방의 제시어만 공개한다.

``` text
A에게 공개: B의 제시어 기린
B에게 공개: A의 제시어 피자
```

게임 종료 전 자신의 실제 제시어는 해당 Player의 REST 응답과 WebSocket
이벤트에 포함하지 않는다.

전체 배정 정보를 모든 Client에 전달한 뒤 Frontend에서 자신의 제시어를
숨기는 방식은 사용하지 않는다.

## 6. 게임 시작 조건

-   GameSession 참가자가 정확히 2명
-   두 Player가 정상적으로 참가 중
-   서로 다른 활성 제시어를 2개 이상 선택할 수 있음

최종 시작 가능 여부는 서버에서 판단한다.

## 7. 게임 진행

게임이 시작되면 각 Player는 화면에서 상대방의 제시어를 확인한다.

질문, 답변, 순서와 실제 추리는 두 Player가 오프라인에서 직접 진행한다.

NOOPI는 다음을 관리하지 않는다.

-   질문 입력
-   질문 내용
-   질문과 답변 기록
-   질문 순서
-   턴
-   답변 입력
-   질문 횟수
-   질문 타이머

## 8. 정답 제출

각 Player는 자신의 제시어를 알아냈다고 생각하면 정답을 제출할 수 있다.

서버는 제출한 답을 요청 Player에게 실제로 배정된 자신의 제시어와
비교한다.

정답 제출은 `GUESSING` 단계의 GameSession 참가자만 수행할 수 있다.

## 9. 오답

오답이면 요청한 Player에게 오답임을 알리고 게임을 계속한다.

오답에 대한 시스템적인 페널티는 없다.

``` text
탈락 없음
턴 변경 없음
시도 횟수 제한 없음
```

오답의 내용이나 제출 사실은 상대방에게 실시간으로 전달하지 않아도 된다.

서버는 오답 응답만으로 GameSession 상태를 변경하지 않는다.

## 10. 정답 판정

정답 판정은 서버에서 수행한다.

클라이언트는 정답 여부를 직접 판단하지 않는다.

기본 정규화는 기존 라이어 게임과 동일하게 적용한다.

-   앞뒤 공백 제거
-   대소문자 차이 무시
-   불필요한 연속 공백 정리

MVP에서는 LLM 기반 의미 판정을 사용하지 않는다.

## 11. 승리 조건

자신의 실제 제시어를 먼저 정확하게 맞힌 Player가 즉시 승리한다.

승자는 서버가 결정하며 정확히 한 명만 존재한다.

승자가 결정되면 GameSession을 `FINISHED`로 변경하고 더 이상의 정답
제출을 허용하지 않는다.

## 12. 동시 정답 제출

두 Player가 거의 동시에 정답을 제출하더라도 서버는 GameSession의 승자
확정을 원자적으로 처리해야 한다.

먼저 유효한 정답으로 승자 확정에 성공한 요청만 게임을 종료할 수 있다.

이미 승자가 확정된 뒤 처리되는 요청은 결과를 다시 변경하거나 두 번째
승자를 만들 수 없다.

구체적인 트랜잭션, Lock 또는 Compare-And-Set 방식은 Backend 구현에서
선택할 수 있으나 다음 불변 조건을 지켜야 한다.

``` text
GameSession당 승자는 최대 1명
FINISHED 이후 승자 변경 불가
```

## 13. 최종 결과

게임 종료 후 두 Player 모두에게 다음 정보를 공개한다.

-   승자
-   A의 실제 제시어
-   B의 실제 제시어

게임 종료 전에는 자신의 실제 제시어를 공개하지 않는다.

## 14. 게임 상태

GameSession 생명주기는 공통 상태를 그대로 사용한다.

``` text
READY
PLAYING
FINISHED
CANCELLED
```

블라인드 게임 내부 phase는 다음과 같다.

``` text
GUESSING
FINISHED
```

`GUESSING`은 상대방의 제시어를 보면서 자신의 제시어를 추리하고 정답을
제출할 수 있는 단계다.

서버는 현재 게임 상태에서 허용되는 행동만 처리한다.

## 15. 실시간 처리

공통 실시간 연결과 Event Envelope를 그대로 사용한다.

게임 시작은 `GAME_STARTED`, 게임 종료와 승자 확정은 `GAME_FINISHED`로
알린다.

상대방의 제시어는 Room 전체 broadcast payload에 포함하지 않는다.
`GAME_STARTED`를 수신한 각 Client가 개인화된 `GET /state`를 조회하여
자신에게 허용된 상대방 제시어를 확인한다.

오답은 GameSession 상태를 변경하지 않으므로 별도 broadcast 이벤트를
발생시키지 않는다.

## 16. 재접속

일시적인 연결 종료만으로 Player를 Room 또는 GameSession에서 즉시
제외하지 않는다.

재접속 후 `GET /state`를 통해 다음 정보를 복구한다.

-   현재 게임 단계
-   상대방 Player
-   상대방의 제시어
-   승자가 결정된 경우 최종 결과

자신의 실제 제시어는 `FINISHED` 전까지 재접속 응답에도 포함하지 않는다.

## 17. Player 이탈

정확히 두 명이 필요한 게임이므로 한 Player의 일시적인 연결 종료 중에는
남은 Player가 재접속을 기다린다.

명시적 Room 나가기 또는 장기 미접속 시 GameSession을 어떻게 종료할지는
별도 운영 정책 결정이 필요하다. 정책 확정 전에는 이탈한 Player를 임의로
패배 처리하거나 남은 Player를 승자로 처리하지 않는다.

## 18. 다시하기

같은 블라인드 게임을 다시 시작하면 새로운 GameSession을 생성한다.

서로 다른 제시어 두 개를 새로 선정하고 배정한다. 이전 GameSession의
제시어, 정답 시도와 결과는 새로운 GameSession에 영향을 주지 않는다.
